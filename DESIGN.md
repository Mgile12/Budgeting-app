## Problem Statement

Mitch wants to build his own envelope-style budgeting app for personal use. He's aware that paid alternatives exist (YNAB, Goodbudget, Monarch, Lunch Money, Copilot) and explicitly does not want to use them. The motivation is craft — he wants the tool shaped around his own rituals. Every transaction is logged manually. Rules plus an LLM advisor handle allocation across goals, taxes, business expenses, bills, and subscriptions. Light animations mark payday and the moment money is delegated to envelopes.

## What Makes This Cool

The soul of the app is the **payday show**. Twice a month, you log "got paid 3200" and the advisor LLM proposes a split across all your envelopes. You see money tokens fly from the paycheck node to each destination envelope — three to five seconds, no sound. You either accept the proposal as-is or tweak it. The animation isn't decoration; it's the moment the app earns being reopened.

Daily logging is intentionally quiet. You tap the **coffee** tile, type **12**, hit save. No animation, no celebration, the envelope just ticks down. The contrast is the point — the daily ritual is calm so the payday moment hits.

## Constraints

- **n=1.** Built for mitch only. No multi-user, no auth, no sharing.
- **Manual input.** No bank sync, no Plaid, no OFX. Every transaction is typed or tapped in.
- **Weekend-shippable.** ~10–13 human-solo hours, ~4–6h with Claude Code driving scaffolding and boilerplate. v1 is meant to be used, then iterated against real use.
- **Local-first.** Data lives on-device (IndexedDB). Tailscale gives phone access without exposing ports.
- **Throw-away-able.** v1 is allowed to be ugly under the hood. The point is to learn what you actually want by using it.
- **Sub-2-second logging.** The bar for the daily ritual.

## Premises

All seven were agreed during the brainstorm:

1. Manual entry is the input contract. No bank sync ever. Sub-2s logging.
2. Single-user, local-first. Storage is local IndexedDB via Dexie. No cloud DB.
3. LLM is an advisor, not an agent. It proposes allocations and parses ambiguous input. No money moves until you tap Accept. Even on payday, the proposal is staged in memory and only writes transactions on explicit accept.
4. The interesting build is the data model and advisor prompt design, not the LLM itself. LLM is plug-in swappable.
5. PWA, responsive. One React app, used on phone and laptop. Tailscale for cafe access.
6. Animations reserved for earned moments. Payday = the show. Goal completion = quiet celebration. Daily logging is calm.
7. Distribution is bookmark + Tailscale. No app store, no installer.

### v1 Scope

**Data model (the 70% that matters)**

Five Dexie tables — kept minimal on purpose. Goals collapse into envelopes; tax config and allocation rules live in the `app_config` singleton; bills and subscriptions share one table because they have the same shape (only label differs).

- `envelopes` — id, name, current_balance (**integer cents**), target_balance (integer cents, nullable; only set for goal envelopes), deadline (nullable ISO date; only set for goal envelopes), color, kind (`bill | subscription | tax | goal | business | discretionary`), order_index, celebrated_at (nullable ISO timestamp; set when target was last crossed, prevents repeat celebration on every render while ≥ target)
- `recurring` — id, name, amount (integer cents), cadence (`weekly | biweekly | monthly | yearly`), next_due (ISO date), envelope_id, kind (`bill | subscription`) — same table for both, only the label and grouping in the advisor prompt differ. **Does not auto-deduct** — `recurring` only informs the payday advisor of upcoming obligations. Actual deductions happen when you log the transaction.
- `transactions` — id, timestamp (ISO 8601 with offset), amount (integer cents, signed), envelope_id, description, source (`tile_tap | text_parse | payday_allocation`), paycheck_id (nullable; set when source is `payday_allocation`)
- `paychecks` — id, timestamp (ISO 8601 with offset), gross_amount (integer cents), allocation_snapshot (JSON cache only — rebuildable by querying `transactions WHERE paycheck_id = ?`; used by the Payday history view to render past allocations without a join storm)
- `app_config` — singleton row: schema_version (integer; starts at 1), `allocation_rule` (ordered array), `top_tiles` (ordered envelope ids — pinned, static in v1), `tax_rate` (number 0..1), `tax_envelope_id`, `discretionary_envelope_id`, `paycheck_cadence`

**Money is integer cents everywhere.** No floats. One formatter (`cents → "$1,234.56"`) at the render boundary. Inputs parse user strings ("12", "12.50", "$12.5") to cents.

**Timestamps are ISO 8601 with the device's local offset.** No UTC conversion — this is a single-device personal tool; the local-time semantics match how you think about "did I log that yesterday."

**Schema versioning:** `db.version(1).stores({...})`. Lock the v1 shape; don't write any `.upgrade()` migrations.

**Derived, not stored:** monthly goal contribution = `(target_balance − current_balance) / months_until_deadline`. Computed in a selector when needed; never written to disk.

**Atomicity:** every balance mutation runs inside `db.transaction('rw', ...)` over the affected tables. Single-tab-open assumption — no cross-tab sync; if two tabs are open, behavior is undefined (acceptable for n=1).

**Overdraw:** a transaction that drives `current_balance` below 0 is allowed and saved. The tile renders in red until the next payday allocation or manual transfer covers it. Not blocked at save time — overdrafts are useful signal.

**Editing a logged transaction:** tap the transaction row in an envelope's recent list → modal with amount, envelope, description. v1 supports amount + envelope reassignment only — no bulk edit, no delete-and-re-add. Save runs a single `db.transaction('rw', ['transactions', 'envelopes'])` that reverses the old delta from the old envelope, applies the new delta to the new envelope, and updates the transaction row. `paycheck_id` is preserved on edit unless the envelope changes; if it changes, `paycheck_id` is preserved but `paychecks.allocation_snapshot` is NOT rewritten — the snapshot is a frozen record of what was proposed and accepted, separate from the editable ledger.

**Three views (only three)**

1. **Home** — envelope tile grid. Each tile shows name, current balance, progress ring (only for goal envelopes with a target), color band. Goal envelope hitting 100% = tile glows (confetti deferred to v1.1). Tap a tile → quick-log modal.
2. **Log** — combo input. Top row of 4–6 quick-tap envelope tiles, sourced from `app_config.top_tiles` (your manual pin order; static in v1 — most-frequent auto-rotation deferred to v1.1, see Open Questions). Free-text input below the tile row handles everything else ("amex 240 dinner"). Tap tile → number pad → save. Or type → LLM parse → confirmation chip → save.
3. **Payday** — landing screen when "got paid X" is logged or the "+ paycheck" button is hit. LLM advisor receives: paycheck amount, app_config rules, current envelope balances, upcoming bills (next 30 days), goal pacing. Returns `[{envelope, amount, reason}]`. UI shows paycheck node at top, target envelopes at bottom, animated money tokens flying top-to-bottom (3–5s). Tally line at bottom shows the discretionary remainder. Accept → writes transactions and updates balances. Edit → adjust amounts inline before accept.

```yaml
  - name: Discretionary

recurring:
  - name: Rent
    kind: bill
    amount: 2400        # dollars in YAML; loadFromConfig() converts to cents
    cadence: monthly
    next_due: 2026-07-01
    envelope: Rent
  - name: Spotify
    kind: subscription
    amount: 11.99
    cadence: monthly
    envelope: Subscriptions

tax_envelope: Tax Savings  # name → resolved to envelope_id at seed time by loadFromConfig()

allocation_rule:
  # Order matters — each step claims from gross before the next runs
  - tax_percentage            # taxes off the top, always
  - cover_bills_next_30_days  # then any bill due in 30d gets its envelope topped to amount
  - subscriptions             # then monthly subscription envelope is topped to next-30d total
  - goal_contributions        # then each goal envelope gets its monthly_contribution
  - discretionary_remainder   # whatever's left lands in Discretionary

top_tiles: [Coffee, Groceries, Gas, Eating Out, Misc]
```

The app reads `config.yml` and seeds Dexie via `loadFromConfig()`. **Seed invariant:** on boot, query `envelopes.count()`. If 0, run `loadFromConfig()` inside one Dexie rw transaction across all tables. If the transaction throws mid-seed, it aborts atomically, `envelopes.count()` stays 0, and the next boot retries. If `count > 0`, skip seeding entirely — a partially populated DB is never re-seeded; partial state means the user is using the app and a re-seed would clobber real data. To re-seed during dev: clear IndexedDB from DevTools, reload. Re-running with a modified config to merge changes is a manual `npm run sync-config` script — out of scope for v1.

**Advisor LLM scope (v1)**

Two LLM call types — that's all:

1. **Text-input parse.** When the user types in the Log free-text bar: raw input → structured JSON `{intent: "transaction" | "paycheck", amount_cents: integer, envelope: string, description: string, confidence: 0..1}`. The LLM self-rates confidence (heuristic, known to be uncalibrated — Settings will let you tune the threshold later). Zod validates the response. Confidence ≥ 0.7 → save with an override-on-tap chip. Confidence < 0.7 → open the manual tile-picker modal with amount pre-filled (no LLM re-prompt loop in v1 — that's v1.1). Paycheck intent (input matches "got paid", "paycheck", "payday" + amount) routes to the Payday view instead of writing a Log transaction.
2. **Payday proposal.** Triggered by `intent="paycheck"` or the explicit "+ paycheck" button. Inputs: paycheck amount (cents), `app_config.allocation_rule`, current envelope balances, `recurring` entries due in the next 30 days, goal pacing (target − current / months_remaining). Output: `[{envelope_id: string, amount_cents: integer, reason: string}]`. Reasons surface under each row ("$1,200 → Rent: covers next month's bill due 2026-07-01"). Rules-based math grounds the proposal — the LLM produces the narrative wrapper and any one-off adjustments ("Coffee is overdrawn — propose $40 from Eating Out"). On accept, **N transactions** are written (one per envelope) inside a single Dexie rw transaction, all linked to the new `paychecks` row via `paycheck_id`. **Discretionary remainder** is written to the envelope referenced by the last `allocation_rule` step (canonically named "Discretionary").

**Allocation proposal lives in component state, not Dexie.** Until you tap Accept, nothing has changed on disk. The payday animation reads from the in-memory proposal object — Framer Motion is not driving off `useLiveQuery` of the envelope table. This avoids render storms and prevents the animation from re-firing if balances change while the proposal is on screen.

**LLM failure fallback.**
- Text-input parse failure → manual tile picker modal with the amount pre-filled. You complete the save by hand.
- Payday proposal failure → the deterministic rule engine runs locally (no LLM narrative) and emits the same `[{envelope_id, amount_cents, reason}]` shape, `reason` filled from the rule name. The flow animation still runs; only the friendly narrative is missing.

**Rules engine.** The fallback path is not optional bonus work — it's the contract for "the app keeps working when the API is down." Spec: a function `runRules(paycheck_cents, app_config, envelopes, recurring) → ProposalRow[]`. Goals are derived inside via `envelopes.filter(e => e.kind === 'goal')`. Each `allocation_rule` step is a named function (`tax_percentage`, `cover_bills_next_30_days`, `subscriptions`, `goal_contributions`, `discretionary_remainder`). The LLM call uses this same function to ground its proposal — then optionally tweaks the rows. The runtime is a remainder counter that starts at `paycheck_cents` and decrements per step.

**`goal_contributions` edge cases:** if a goal envelope's `deadline ≤ today` or is null, skip it in the allocation and surface a "review goal" badge on the Home tile. If `current_balance ≥ target_balance`, also skip — the goal is funded.

**`discretionary_remainder` destination:** `app_config.discretionary_envelope_id` (resolved from `discretionary_envelope` name in `config.yml` at seed time). Whatever cents are left after the earlier steps are written to this envelope.

No other LLM calls in v1. No proactive scheduling. No real-time overspend flagging. Those are v2.

**Animation work (build LAST)**

- **Envelope tile fill bar** — Framer Motion `animate` on a progress bar when balance changes.
- **Goal completion** — CSS glow on the tile when `current_balance` first crosses `target_balance`. Uses the `celebrated_at` field on `envelopes` to fire exactly once per crossing — set on the crossing transaction, cleared if balance later drops below target. Confetti deferred to v1.1; CSS glow alone is enough for v1.
- **Payday flow** — paycheck node at top, target envelopes at bottom, money-token components animated origin→destination with Framer Motion. Stagger by allocation order. Total ~3–5 seconds. Driven by the in-memory proposal object, not by Dexie live queries.

**Stack pick (final)**

- Vite + React + TypeScript
- Tailwind CSS (skip shadcn/ui for v1 — adds weight without earning it at this scope)
- Framer Motion
- Dexie (IndexedDB wrapper)
- Zod (LLM response validation)
- js-yaml — `config.yml` imported as raw text via Vite's `?raw` suffix (`import yamlText from './config.yml?raw'`), parsed at boot. Accepted tradeoff: editing config requires `npm run dev` to pick up the change (Vite HMR handles this on save). For a "real" hot-edit story, switch to `fetch('/config.yml')` later — out of scope for v1.
- Anthropic SDK — key in `.env.local` as `VITE_ANTHROPIC_KEY`; constructor needs `dangerouslyAllowBrowser: true`. Pinned model: `claude-haiku-4-5-20251001`. Per-call params: `max_tokens: 512` for text-parse, `max_tokens: 2048` for payday proposal; 10-second timeout via `AbortController` on both. Client-side rate guard: at most one parse call in flight at a time, 500ms minimum spacing between calls (debounced from the input). Only acceptable in-bundle because access is Tailscale-gated. Set a hard monthly spend cap in the Anthropic console as belt-and-suspenders: a stolen/lost device on the Tailnet still can't run up your bill past the cap.
- **Navigation:** state-based view switch (single `useState<'home' | 'log' | 'payday'>` at app root), no router. Three views don't earn a dependency.
- No backend, no auth, no deployment.

## Open Questions

1. **API key + future-of-Tailscale.** Covered in Stack pick and Distribution Plan — `VITE_ANTHROPIC_KEY` lives in the bundle, safe only on Tailscale, future-leave-Tailscale path is a Bun BFF. Listed here only to flag it as a known sharp edge to monitor; not a decision to make in v1.
2. **What if you forget to log a paycheck?** v1: nothing — payday is triggered by you. v2: cadence-aware reminder ("last paycheck was 16 days ago, expected every 14 — log one?").
3. **Backup.** v1 ships with a manual "Export JSON" button. Phone wipe = data loss unless you remember to export. v1.5: auto-export to a Tailscale-shared folder. v2: BFF + `gh` CLI for private GitHub repo backup.
4. **Ambiguous transaction text.** "$40 Amazon" could be Groceries, Household, or Misc. v1: LLM picks highest-confidence envelope; confirmation chip overrides before save. If confidence < 0.7 the LLM is prompted to ask one clarifying question instead of guessing silently.
5. **Goal pacing surplus.** Should the advisor proportionally accelerate a goal when discretionary is unusually fat? v1: no — remainder stays in Discretionary. The user decides whether to manually shift it. v2: advisor can suggest.
6. **True PWA install on iOS.** Requires HTTPS to the dev server. Tailscale's MagicDNS doesn't issue certs to the in-network hostname. Options for v1.5: run `vite build && vite preview` behind Tailscale Funnel (real cert, public-facing), or a local caddy reverse-proxy with a self-signed cert your phone trusts. Either way, v1 accepts the webclip behavior.
7. **Tile-picker fallback vs LLM clarifying re-prompt.** v1 uses tile-picker on low confidence (no second LLM call). v1.1 may add a one-shot clarifying re-prompt if the picker proves too tap-heavy in real use — the diagnosis comes from actually using the app.
8. **LLM confidence calibration.** Self-rated confidence is uncalibrated and the 0.7 threshold is a guess. v1.1 likely adds a Settings toggle that logs every confidence-result pair so you can tune the threshold from your own data.
9. **Most-frequent auto-rotation of top tiles.** v1.1. Rule sketch when it lands: top 5 envelopes by transaction count over the last 30 days, ties broken by most-recent use; goal envelopes within 2 weeks of deadline stay pinned regardless. Skipped in v1 because static `top_tiles` works and saves a chunk of edge-case logic.
