## Problem Statement

Mitch wants to build his own envelope-style budgeting app for personal use. He's aware that paid alternatives exist (YNAB, Goodbudget, Monarch, Lunch Money, Copilot) and explicitly doesn't want them. The motivation is craft — the tool shaped around his real life.

His real life: **one ~$6,000 monthly retainer at end of month funds the entire next month** (tax, all bills, all subs, goal contributions, discretionary). Every other deposit is bonus. The app is the system that converts the retainer into envelope allocations, watches the spending against projections, whispers via Telegram when something needs his attention, and tells him the truth in plain language at month-end.

## What Makes This Cool

Five moments earn the project:

1. **The retainer show** — once a month, ~$6k splits into the right envelopes with a 3–5 second money-token flow. The main event.
2. **The bonus light show** — every non-retainer deposit defaults to the nearest-deadline unfunded goal with a quieter animation. Different ceremony for different income.
3. **The Telegram coach** — speaks at most once a day. Warns about runway and goal slip. Occasionally says "you're on pace, nothing to do." Never accepts input. Calm tap on the shoulder, not noise.
4. **The monthly review** — narrative-first verdict from the LLM ("you overspend in the three days after you skip logging"), grounded in deterministic stats. Diagnostic *and* prescriptive.
5. **The projection engine** — turns raw balances into actionable signal by separating "underspent" from "not spent yet."

Daily logging is intentionally quiet — tap a tile, type, save. Calm so the moments above hit by contrast.

## Constraints

- **n=1.** Built for Mitch only. No multi-user, no public auth flow.
- **Manual input.** No bank sync, no Plaid, no OFX. Every transaction is typed or tapped.
- **Self-hosted on Mitch's own domain.** Real HTTPS, real PWA, key never in the browser bundle.
- **Monthly retainer cycle.** Retainer date roughly the 28th–1st; bonuses arrive whenever.
- **Sub-2-second logging.** Bar for the daily ritual.
- **Always-on backend.** Required for scheduled jobs (projection refresh, coach dispatcher, monthly review generation) and to hold the Anthropic key server-side.
- **Telegram outbound only.** The bot never accepts input from Mitch. Logging is exclusively in the web app.

## Premises

All aligned to USER-STORIES.md:

1. **Manual entry is the input contract.** No bank sync. Sub-2s logging.
2. **Self-hosted on Mitch's own domain.** HTTPS, server-side Anthropic key, shared datastore both web app and backend read.
3. **LLM is an advisor, not an agent.** It parses, proposes, narrates. Nothing moves money without an explicit Accept.
4. **One real budget cycle: retainer-to-retainer.** Bonus deposits skip obligation math.
5. **Telegram is outbound only.** Five message types, batched ≤1 per day. Calm presence, not chatbot.
6. **Projection over current-balance everywhere.** Coach alerts, money-move suggestions, goal pacing all read from the projection engine, not raw balances.
7. **Animations reserved for earned moments.** Retainer = full show. Bonus = light show. Goal completion = quiet glow. Daily logging is calm. Review = words first, charts as support.

## Architecture: Approach B — Self-Hosted

```
┌─────────────────┐   HTTPS    ┌─────────────────────────────────┐
│  React PWA      │ ─────────▶ │  Bun backend                    │
│  (browser /     │ ◀───────── │  ├─ HTTP API (Hono)             │
│   home-screen)  │            │  ├─ SQLite via Drizzle          │
└─────────────────┘            │  ├─ Anthropic SDK (server-side) │
                                │  ├─ Scheduled jobs              │
                                │  └─ Telegram Bot API (outbound) │
                                └────────────┬────────────────────┘
                                             │
                                       ┌─────▼──────┐
                                       │ SQLite     │
                                       │ file       │
                                       └────────────┘
```

**Hosting target.** A single VM (DigitalOcean / Hetzner / home server) or a managed Bun host (Render, Railway). Domain points at the VM. **Caddy** in front of the Bun process handles HTTPS via Let's Encrypt automatically. SQLite is a single file on disk; backup is `cp` to a Tailscale-shared folder or S3 nightly.

**Why Approach B now (not the original Approach A).** The product evolved to need:
- Scheduled jobs (projection refresh, coach dispatcher, monthly review) — requires an always-on process, not a browser.
- A Telegram bot — requires server-side identity and an outbound channel.
- Anthropic key safety — server-side instead of in the bundle, so the key can't leak via DevTools or a stolen device.
- A real PWA — HTTPS on a real domain unlocks proper service worker + install prompt that Tailscale-over-HTTP couldn't.

## Data Model

**Eight SQLite tables via Drizzle ORM.** Money is stored as integer cents everywhere; one formatter at the render boundary. Timestamps are ISO 8601 with the device's local offset. Schema versioning via Drizzle's `drizzle-kit generate` migrations; lock the v1 shape, write a migration for any change.

### Core domain

- `envelopes` — id, name, current_balance (cents), target_balance (cents, nullable; goals only), deadline (nullable ISO date; goals only), color, kind (`bill | subscription | tax | goal | business | discretionary`), order_index, celebrated_at (nullable ISO timestamp)
- `recurring` — id, name, amount (cents), cadence (`weekly | biweekly | monthly | yearly`), next_due (ISO date), envelope_id, kind (`bill | subscription`). **Does not auto-deduct** — only informs the allocation advisor of upcoming obligations. Actual deductions happen when Mitch logs the transaction.
- `transactions` — id, tx_date (ISO date, the date *the spend happened* per story 1.6), created_at (ISO timestamp, when the row was written), amount (cents, signed), envelope_id, description, source (`tile_tap | text_parse | allocation`), deposit_id (nullable; set when source is `allocation`)
- `deposits` — id, ts (ISO timestamp), gross_amount (cents), kind (`retainer | bonus`), allocation_snapshot (JSON — frozen record of what was proposed and accepted)
- `app_config` — singleton row: schema_version, `allocation_rule` (ordered array), `top_tiles` (envelope ids), `tax_rate`, `tax_envelope_id`, `discretionary_envelope_id`, `retainer_amount_cents` (heuristic anchor, ~600000 for $6k), `retainer_cycle_start` (which calendar day starts the cycle, e.g. 28), `cycle_avg_window_cycles` (how many cycles to average for projection, default 3)

### Coach + review + projection (new)

- `projections` cache — envelope_id (PK), computed_at, current_balance (cents), avg_cycle_spend (cents), projected_remaining_spend (cents), slack (cents), on_pace (bool), confidence (`cold | learning | learned`)
- `coach_log` — id, ts, kind (`runway | envelope_runway | goal_slip | positive | review_ready | nothing_logged`), payload (JSON), telegram_message_id (nullable; set after successful Telegram POST)
- `coach_state` singleton — chat_id (the Telegram chat to message), enabled (bool), dispatch_time_local (e.g. "20:00"), last_dispatch_date (ISO date), last_fire_per_kind (JSON map: `{ runway: "2026-06-04", ... }` — prevents duplicate fires)
- `monthly_reviews` — id, cycle_start (ISO date), cycle_end (ISO date), generated_at, llm_narrative (text), deterministic_stats (JSON), notified (bool — was the "review ready" Telegram fired)

### Invariants

- **Money is integer cents everywhere.** No floats. One formatter at render.
- **All balance mutations atomic.** Every API endpoint that touches balances wraps its DB writes in a Drizzle transaction.
- **Seed-once.** `loadFromConfig()` runs only if `envelopes` is empty. Partial state is never re-seeded.
- **Editable ledger, frozen snapshots.** `transactions` is the editable source of truth. `deposits.allocation_snapshot` is a frozen record of what was originally proposed and accepted; never rewritten by edits.
- **Overdraw allowed.** Saves never block on a negative balance. Red tile is the signal; the projection engine factors it into runway.

## v1 Scope — User-facing surfaces

### Four tabs

1. **Log** (default landing every open) — tile row of `app_config.top_tiles` + free-text bar + confirmation chip + LLM-down corner icon. Default date is *now*; tap to set a different date (story 1.6).
2. **Home** — envelope tile grid. Each tile: name, current balance, progress ring (goals only), color band. Overdrawn tile renders in red with "Overdrawn -$X". Goal hitting 100% glows once via `celebrated_at` gate. Money-move suggestions appear as a quiet, dismissible chip on the relevant tile when an envelope goes negative.
3. **Review** — stand-alone surface. Top: LLM-narrated verdict (paragraph). Middle: 1–2 small supporting charts (spend by envelope over the cycle, goal pace). Bottom: deterministic stats. Read any time; current month plus history of prior reviews.
4. **Settings** — gear icon top-right of Home. Houses: Telegram connect flow (paste bot token + chat_id once), Export/Import JSON, "Last backup: N days ago" chip, total budget overview, schema_version, coach kill switch.

### Allocation flow (entered from Log, not a tab)

Triggered by a deposit-intent log entry OR the "+ deposit" button on Log. Two modes:

**Retainer mode (the full show).** Triggered when amount is within ±10% of `retainer_amount_cents` AND tx_date is within `retainer_cycle_start ± 5 days`, defaulted on. A single chip at the top: "Retainer or Bonus?" with **Retainer** selected; one tap to switch. The deterministic rules engine + LLM advisor produces the proposal across `tax_percentage → cover_bills_next_30_days → subscriptions → goal_contributions → discretionary_remainder`. UI: paycheck node at top, target envelopes at bottom, 3–5s money-token flow staggered 300ms apart, reasons under each row, inline edit with Discretionary as the elastic envelope. Accept commits N transactions in a single Drizzle transaction linked via `deposit_id`.

**Bonus mode (the light show).** Triggered for any non-retainer deposit. The rules engine skips obligations and **proposes the full amount to the nearest-deadline unfunded goal** (per story 3.2). Light show: paycheck node at top, single token flies to the target goal envelope, ~1.5 seconds. Override allows holding in Discretionary or sending elsewhere; same inline-edit affordance as retainer mode.

**Under-paycheck behavior (retainer only).** If `tax + bills + subs + goal_contributions` exceeds the retainer amount, the rules engine truncates the last unmet rules — bills and tax are honored first, goals get $0 if money runs out, discretionary stays at $0. A yellow chip: "Bills + tax covered. Goals deferred this cycle. Discretionary: $0." Story 2.8 wants this to be a **rare, loud alarm** because the retainer is sized to cover everything — the alarm IS the chip + a Telegram coach message of kind `runway` fires the same day.

**Editing during allocation.** Inline edit per row before Accept. Discretionary is the single elastic envelope that absorbs the delta. Sum invariant enforced on every keystroke; Save disabled while invalid. Editing the Tax row is allowed but warned ("overrides your tax rate — remember at year-end"). Negative amounts blocked.

### The Telegram coach

Outbound only. The bot never accepts input. Five message types:

| Kind | When fires | Cadence |
|---|---|---|
| `runway` | Projection says total money-left runs dry ≥2 days before the next retainer | Once per crossing into danger |
| `envelope_runway` | A single envelope projected to run dry before the next retainer | Once per envelope per crossing |
| `goal_slip` | A goal falls behind its required pace (target − current vs months_remaining) | Once per slip |
| `positive` | Nothing to warn about and at least 6 days since last positive ping | At most weekly |
| `review_ready` | A monthly_review row was generated | Once per review |
| `nothing_logged` | A full local-day passed with zero transactions | At most once per quiet day |

**Dispatcher schedule.** A scheduled job runs at `coach_state.dispatch_time_local` (default 20:00 Mitch's local TZ) every day. It evaluates conditions in priority order (runway > envelope_runway > goal_slip > review_ready > nothing_logged > positive) and fires **at most one message per day total**. Each fire writes to `coach_log` and updates `coach_state.last_fire_per_kind`.

**Message shape.** Plain text. LLM-generated narrative grounded in deterministic projection data. Example: "Eating Out is on pace to run dry on the 22nd, 4 days before your retainer. You're $18 over the cycle average so far. Pull $40 from Discretionary or slow down — your call."

**Connect flow.** Settings → "Connect Telegram" → instructions to message `@BotFather`, get a bot token, get a chat_id via a one-time `/start`. Paste both into the form, save. Stored in `coach_state`. One-time setup.

### Projection engine

Per-envelope, computed every 4 hours by a scheduled job and cached in the `projections` table. Pseudo-API:

```ts
function projectEnvelope(envelopeId: string): {
  current_balance: number,        // cents
  avg_cycle_spend: number,        // cents — mean spend per cycle over the avg window
  projected_remaining_spend: number, // cents — what this envelope is on pace to spend through cycle end
  slack: number,                  // current_balance - projected_remaining_spend
  on_pace: boolean,               // slack >= 0
  confidence: "cold" | "learning" | "learned"
}
```

**Cold-start window.** Until an envelope has ≥3 completed cycles of data, confidence is `cold` and projection treats expected spend = `avg_recurring_amount * cycle_fraction_remaining` (conservative — assumes you'll spend the full cycle average ratably). At 3+ cycles with a stable cadence (variance < 25%), confidence flips to `learned` and projections use the actual cycle pattern. Between: `learning` — half-weight blend.

**Runway aggregate.** `runway = sum(slack_i)` across non-goal envelopes. Days-to-retainer is computed from `app_config.retainer_cycle_start` and today's date. Coach `runway` fires when projected aggregate slack ≤ 0 with ≥2 days of cycle remaining.

**Inputs to LLM advisor.** Every payday proposal and every coach message receives the projection snapshot — the LLM speaks from grounded state, not raw balances.

### Money-move helper

Quiet, dismissible chip that appears on Home when an envelope goes negative (story 7.1). One-tap reveals a proposed source envelope (per story 7.3, the projection engine picks the envelope with the most slack — never one Mitch is about to spend from). Two buttons: **Move** (commits a transfer transaction) and **Dismiss** (hides the chip for this envelope until next negative crossing).

**Cold-start guard.** If projection confidence for any envelope is `cold`, the helper only proposes pulls from Discretionary and **asks** before moving instead of one-tap commit (story 7.4).

### Monthly review

Generated once per cycle by a scheduled job on `retainer_cycle_start + 0` at 09:00 local. Inputs to the LLM: full transactions for the prior cycle, projection history, goal progress deltas, recurring vs actual spend. Output:

1. **Narrative verdict** (text, the lead): patterns the LLM noticed (story 5.3 — "you overspend in the days after you skip logging"), goal pace, what to keep doing, what to improve.
2. **Deterministic stats** (JSON, what the LLM grounded in): spend per envelope vs avg, days you didn't log, goals that slipped, goals that funded, retainer underspend or overspend.
3. **1–2 supporting charts** (story 5.5): spend-by-envelope bar chart and goal-pace line. Supporting, not leading.

Generated reviews persist in `monthly_reviews`. The Review tab shows the current month at top, then collapsible history. Story 5.4: numbers come from deterministic stats — the LLM narrates but **cannot invent figures.**

## Advisor LLM Scope

All LLM calls happen server-side. The backend exposes endpoints; the frontend never sees the Anthropic key.

Four call types in v1:

1. **Text-input parse** — `POST /api/log/parse` — input: raw text. Output: `{intent: "transaction" | "deposit", amount_cents, envelope, description, confidence}`. Confidence < 0.7 → frontend opens tile-picker fallback with amount pre-filled. Deposit intent routes to Allocation flow.
2. **Allocation proposal** — `POST /api/allocation/propose` — input: `{deposit_cents, kind, app_config, envelopes, recurring, goals_with_pacing, projection_snapshot}`. Output: `{proposal: [{envelope_id, amount_cents, reason}], narrative: string, mode: "retainer" | "bonus"}`. Rules engine baseline runs first (deterministic floor); LLM tweaks on top; Zod validates; sum-equals-deposit check; fallback to baseline on any failure.
3. **Coach message narration** — `POST /api/coach/narrate` (internal, called by the dispatcher) — input: `{kind, payload}` from the condition check. Output: `{text: string}` ≤ 280 chars. Deterministic fallback: `kind`-specific template strings if LLM fails.
4. **Monthly review narrative** — `POST /api/review/narrate` (internal, called by the monthly scheduler) — input: deterministic stats blob. Output: `{narrative: string}` ≤ 800 words. Fallback on failure: simple template ("This cycle: $X spent, Y goals progressed, Z slipped") — review still ships, just less colorful.

All call types use **Claude Haiku** (`claude-haiku-4-5-20251001`) for cost. `max_tokens` per type: parse 512, allocation 2048, coach 256, review 2048. 10-second AbortController on each. Zod validates every response at the boundary.

**LLM failure is never blocking.** Every path has a deterministic fallback. A subtle 8px corner icon on the Log input bar surfaces "last LLM call errored" and auto-clears on next success — the only UI surface that exposes LLM-down state.

## Animation work

- **Envelope tile fill bar** — Framer Motion `animate` on a progress bar when balance changes. Reverses on transaction edit.
- **Goal completion** — CSS glow on the tile when `current_balance` first crosses `target_balance`. `celebrated_at` field fires exactly once per crossing; cleared if balance drops below target. Confetti deferred to v1.1. **Timing:** if crossed during an allocation, glow fires on the post-Accept Home re-render — NOT during the allocation animation. Multiple goals hitting target stagger 1.5s in `order_index` order.
- **Retainer flow (full show)** — paycheck node at top, target envelopes at bottom, money-token components animated origin→destination with Framer Motion. Token text size scales by `log(amount_cents)`. Token color matches destination envelope. One token at a time, 300ms stagger. Total ~3–5 seconds. Driven by the in-memory proposal object, not by live DB queries. Silent by default.
- **Bonus flow (light show)** — single money token flies from paycheck node to the target goal envelope. ~1.5 seconds. Same easing curve, same silent behavior. Light by design.
- **Reduced-motion gate.** All animations respect `@media (prefers-reduced-motion: reduce)`: tokens don't fly (rows fade in at the same 300ms stagger), envelope fill bar snaps, goal glow becomes a non-pulsing colored border. Same information, no movement.

## Backend stack (final)

- **Runtime: Bun** (latest LTS). Native TypeScript, fast cold start, built-in fetch + sqlite, single-file binary if needed.
- **HTTP framework: Hono.** Tiny (~12 KB), Bun-friendly, zero decorators. Routing + middleware in one import.
- **DB: SQLite via `bun:sqlite` + Drizzle ORM.** Typed schemas. Migrations via `drizzle-kit`.
- **Validation: Zod.** Every API boundary + every LLM response.
- **Anthropic: `@anthropic-ai/sdk`.** Server-side, key from env (`ANTHROPIC_API_KEY`).
- **Telegram: direct HTTP via fetch.** Outbound only is just `POST https://api.telegram.org/bot${TOKEN}/sendMessage`. No SDK needed.
- **Scheduled jobs: `setInterval` in the Bun process.** Three jobs: projection refresh (every 4h), coach dispatcher (daily at `coach_state.dispatch_time_local`), monthly review generator (daily check, fires on `retainer_cycle_start`). Single process means single source of truth for state.
- **Auth: bearer token in env.** One value (`AUTH_TOKEN`). Frontend stores in localStorage after one-time paste on first visit. Every API request sends `Authorization: Bearer <token>`. n=1 — no user system, no OAuth.
- **Caddy in front.** Handles HTTPS via Let's Encrypt automatically. `caddyfile` is ~5 lines.

## Frontend stack (final)

- Vite + React + TypeScript
- Tailwind CSS (skip shadcn/ui — adds weight without earning it)
- Framer Motion
- Zod (LLM response shapes from the API)
- React Query (or SWR) for API data — caches envelopes, projections, allocation proposals; invalidates on writes
- No IndexedDB. The SQLite-backend is the datastore. Service worker caches static assets for offline shell only; real data needs network.
- **Navigation:** state-based view switch (single `useState<'log' | 'home' | 'review' | 'settings'>` at app root), no router. Four views don't earn a dependency. **Default view on every mount is `'log'`.**
- **Two-tab guard:** `BroadcastChannel('budget-app-v1')`. Second tab shows "Already open in another tab. Refresh to take over." Stays read-only until refreshed.

## API surface (sketch)

```
GET    /api/envelopes                  → current balances + projection snapshot
GET    /api/transactions?envelope=X    → recent transactions per envelope
POST   /api/transactions               → log one (body: {amount_cents, envelope_id, tx_date, description, source})
PATCH  /api/transactions/:id           → edit one (amount, envelope_id, tx_date)

POST   /api/log/parse                  → free-text → structured (LLM)
POST   /api/deposits                   → log deposit + kick allocation flow (body: {amount_cents, kind, ts})
POST   /api/allocation/propose         → returns proposal (LLM + rules)
POST   /api/allocation/accept          → commits N transactions atomically (body: {proposal, deposit_id})

GET    /api/projection                 → cached projection snapshot
POST   /api/projection/refresh         → on-demand recompute (rarely called by UI)

GET    /api/review/current             → current cycle review (lazily generates if missing past anchor date)
GET    /api/review/history             → list of prior reviews

POST   /api/coach/connect              → set chat_id + token (Telegram)
PATCH  /api/coach/settings             → enable/disable, dispatch_time_local

POST   /api/export                     → download JSON of all tables
POST   /api/import                     → restore from JSON (wipes + reseeds inside one transaction)
```

All endpoints require `Authorization: Bearer <token>`. Bad token returns 401 with no further detail.

## Deployment + hosting

**Recommended path for v1:**

1. Buy a small VM (DigitalOcean $6/mo droplet, Hetzner CX11 €4/mo, or a home server). Ubuntu 24.04 LTS.
2. Point your domain (or a subdomain like `budget.mitch.example`) at the VM's IP.
3. Install Bun, Caddy, sqlite3. Clone the repo. Build the frontend with `bun run build` (outputs to `dist/`).
4. Caddy serves `dist/` for non-API routes and reverse-proxies `/api/*` to Bun on `:3000`.
5. Bun process managed by systemd. `ANTHROPIC_API_KEY`, `TELEGRAM_BOT_TOKEN`, and `AUTH_TOKEN` in `/etc/systemd/system/budget.service.d/secrets.conf` (mode 600, root-owned).
6. SQLite file at `/var/lib/budget/budget.db`. Nightly cron: `sqlite3 budget.db ".backup '/backup/budget-$(date +\%Y\%m\%d).db'"` then rsync to a Tailscale-shared folder or S3.

**HTTPS.** Caddy auto-provisions Let's Encrypt certs. Real PWA install works on iOS now (story 0.1).

**Single-tenant.** No multi-user, no user table. The bearer token IS the auth.

## Open Questions (carries USER-STORIES Open Decisions + new)

Resolved in this design:

| Q | Decision |
|---|---|
| Retainer vs bonus detection | **Explicit toggle** at Allocation flow entry, defaulted to Retainer when amount is within ±10% of `retainer_amount_cents` AND tx_date is within `retainer_cycle_start ± 5 days` |
| Projection cold-start threshold | **≥3 completed cycles per envelope** before `learned` confidence; variance < 25% required for stable. Between is `learning` (half-weight blend). |
| Runway danger threshold | **Projected aggregate slack ≤ 0 with ≥2 days of cycle remaining.** Actionable but early. |
| Positive-ping frequency | **At most weekly**, only when nothing else to warn about. |
| Nothing-logged cadence | **Once per quiet day**, fires at next dispatch window. Resets on any log. |

Still open for Mitch:

1. **Hosting choice.** Managed (Render / Railway / Fly.io) vs unmanaged VM (DO / Hetzner). Managed = less ops, ~$5–10/mo + DB. Unmanaged = $4–6/mo, full control, ~30min initial setup.
2. **Domain.** Use a subdomain of an existing domain or buy a fresh one for this. Decision matters only for what the URL reads as.
3. **Telegram bot identity.** Bot name + handle when you create it with BotFather. (Doesn't affect functionality; just an identity decision.)
4. **Goal definition.** Real envelopes, real bills, real subscription list, real tax rate, real goals with targets and deadlines in `config.yml` — **the assignment, unchanged from prior design.**
5. **Service worker offline strategy.** v1: cache static assets only, fail loudly when offline. v1.5: queue writes locally and replay on reconnect. v2: full offline-first with conflict resolution. v1 acceptable because n=1 device is rarely offline for long.

## Success Criteria

v1 is "done" when **for two consecutive retainer cycles**, all of:

- Every transaction is logged on the day it happened (or backdated within 48h via tx_date).
- One retainer has been allocated through the full show.
- At least one bonus has been logged through the light show.
- The Telegram coach fired at least one alert that prompted you to act before payday.
- The monthly review for the first complete cycle read like it knew you — at least one specific pattern called out.
- The retainer-show animation made you smile at least twice.
- You did not fall back to a spreadsheet or another budgeting app.

If by cycle 3 you've stopped logging, v1 has failed. Diagnose: was input too slow? Did the coach feel like nagging? Did the review feel like horoscope? That diagnosis is the brief for v1.1.

## Distribution Plan

n=1, but real production:

- Code lives in a single repo (this one).
- CI/CD: GitHub Actions on push to main → build frontend, ssh to VM, restart Bun. Optional v1, manual deploy is fine.
- The app lives at `https://budget.yourdomain.example` (or wherever).
